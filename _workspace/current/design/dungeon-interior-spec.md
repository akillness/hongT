## 0. 요약

현재 던전은 **방이 없다.** 장애물 없는 타원 하나이고, 환경은 전부 절차적 큐브이며,
충돌은 원기둥 1종뿐이다. 이 스펙은 세 가지를 동시에 바꾼다.

| | 현재 [OBSERVED] | 제안 [TARGET] |
|---|---|---|
| 플레이필드 | 타원 half 520×270, 면적 441,079 u² | 타원 half 735×390, 면적 900,538 u² (**2.04×**) |
| 이동 가능 면적 | 425,999~441,079 u² | 769,744~811,936 u² (**1.75~1.84×**) — §3.4 실측 |
| 충돌 종류 | 원기둥 1종 (`ObsidianPillar`) | 원기둥 + **캡슐 벽** 2종 |
| 회피 | 없음 (밀어내기만 → 적이 낌) | 벽 슬라이딩 + 접선 조향 |
| 순환 구조 | 없음 (레인 0, 루프 0) | 엄폐 격자 + 스파인 2 · 막다른 길 0 (§3.3에서 레인 문법 은퇴) |
| 환경 메시 | 유닛 큐브 + 쿼드 2개 | 건축 킷 10 + 충돌 프롭 8 + 장식 10 + 텍스처 5 |

**가장 중요한 발견 하나.** `SimConfig.WorldWidth`/`WorldHeight`(1536×1024)는
**정의부 외에 어디에서도 참조되지 않는 死상수**다 (전수 grep, `Assets/Scripts/` ·
`Assets/Tests/`). 실제 구속은 도색 플레이트(sim x ±850 · y 0..1024,
`EnvironmentBuilder.cs:1066`, `:617`)이고, 2.04× 확장은 **플레이트를 다시 그리지 않고
들어간다.** 인터뷰 때 제가 제시한 프리뷰의 "배경 플레이트 y 0..1024 → y −180..1388"
항목은 **불필요합니다 — 작업 목록에서 뺍니다.**

## 2. 확장 기하 계약 [TARGET]

### 2.1 안 A (권장) — half 735 × 390

```
플레이필드   타원 half 735 × 390   중심 (768, 604)
면적         900,538 u²            현재 441,079 대비 2.0416×
bbox         x 33..1503 · y 214..994   (1470 × 780)
플레이어 도달 half 701 (e 0.954, margin 34)
적 정지선     half 711 (e 0.967, margin 24)
```

**왜 이 값인가 — 세 구속을 동시에 만족하는 최대치.**

1. **도색 플레이트.** x ±850(→ x −82..1618) 안에 벽 링(e 1.02 → x 18..1518)이 들어간다.
   여유 100 px. y는 0..1024 안에 y 214..994가 들어간다. **재도색 불필요.**
2. **카메라.** D 17.5에서 초점면 프러스텀 half-width = `17.5 × tan21° × 1.5 = 10.076 u`.
   새 아레나 half = `735 × 0.0125 = 9.1875 u`. 프레임이 **e 1.097**에 떨어지고 벽 링이
   e 1.02이므로 **7.5 % 여백으로 벽이 프레임 안에 들어온다.** 카메라 거리 변경 0.
3. **애시월.** 새 edge 33 / 1503, 중심 768 → 반폭 735. 현재 오버슛(+40)을 보존하려면
   `WallDepthMax` 560 → 775.

**이동 가능 면적**: [OBSERVED] **685,440~755,632 u² = 1.554~1.713×** (스테이지별,
스파인 수에 따라). 산출은 §3.4 하나뿐이다 — 초안이 여기 적었던 1.720×는 액터 반경을
빠뜨린 예산에서 나온 값이고 §3.4에서 정정했다.

(CLAUDE.md §4c — 뷰 결함은 화면을 열어야만 보인다).
**안 B는 "이동 가능 면적도 2배"를 명시적으로 원할 때만.** 승인 시 택일해 주십시오.

### 2.4 폐기되는 것 — 외곽 실루엣 링과 Zone C

두 안 모두에서 **`AddOuterSilhouettes` (e 1.35/1.50)와 Zone C 링 (e 1.22)은
플레이트 밖으로 나간다.**

```
안 A에서 x축 최대 e = 플레이트 850 / half 735 = 1.156   →  Zone C(1.22)조차 밖
```

이건 결함이 아니라 **설계 신호**다. 실루엣 링의 존재 이유는 코드 주석에 적혀 있다 —
"Zone C가 e 1.22에서 끝나는데 플레이트가 e 1.63까지 가서 그 애뉼러스가 맨바닥"
(`EnvironmentBuilder.cs:1004-1010`). 확장하면 **그 빈 애뉼러스 자체가 사라진다.**

→ **경계는 원거리 실루엣이 아니라 실제 벽 링이 된다.** 이게 이번 개편의 핵심 전환이고,
"인테리어 구성"이라는 요구에 정확히 대응한다. 바깥에 흩어 세운 조각상 대신 **방을 두르는
벽**이 경계다.

**제거 대상**: `AddOuterSilhouettes`, `AddZoneC`, `SilhouetteE/SilhouetteEOuter`,
`PlateBottomY` 기반 남측 에이프런 로직. **신설**: `AddBoundaryWallRing`.

## 3. 인테리어 구성 — 3레인 그래머

### 3.1 왜 동심원이 아니라 레인인가

첫 초안은 동심 밴드(코어 / 회랑 / 베이 / 벽)였고 **산술로 반증됐다.**
통로 최소폭을 만족하려면 밴드 두께가 x축 Δe ≥ 130/735 = 0.177, **y축 Δe ≥ 150/390 = 0.385**
필요하다. y 방향엔 e 1.0을 4밴드로 나눌 여유가 없다 (0.385 × 4 = 1.54 > 1.0).

**종횡비 1.885 타원에서 동심 분할은 y축에서 물리적으로 불가능하다.**
리서치가 권하는 형태(레인 1~3개, 장축 방향)가 기하와도 일치한다.

### 3.2 레인 배치

y 780 px를 3레인 + 2스파인으로 나눈다. 스파인 = 캡슐 벽, 반경 24
(`EnvironmentLayout.WallThicknessPx = 24`와 동일 — 새 상수를 만들지 않는다).

```
y 214 ┌─────────────────────────────────────────────────────┐
      │  레인 N   (228 px)   상단 회랑                        │
y 442 │◀ 개구 ▶╞═════════╡ 통로 ╞═════════╡◀ 개구 ▶│          스파인 N (y 442..490)
      │                                                     │
y 490 │  레인 M   (228 px)   중앙 성소 — 포컬 · 네거티브       │
y 718 │◀ 개구 ▶╞═════════╡ 통로 ╞═════════╡◀ 개구 ▶│          스파인 S (y 718..766)
      │                                                     │
y 766 │  레인 S   (228 px)   하단 수로                        │
y 994 └─────────────────────────────────────────────────────┘

        개구 ≥ 300 px (§3.3 — 경계에 닿으면 조향이 못 돈다)
        통로  = 205 px, 스테이지당 1~2개
```

**레인 폭 검증**: 228 px − 2 × 26(플레이어 반경) = **176 px 자유 이동폭** ≥ 최소 150 ✓.

### 3.3 스파인은 대부분 은퇴했다 — **2026-08-11, 실측으로**

초안(§3.2)은 3레인 스파인 문법이었다. **이 게임의 기믹 밀도와 양립하지 않는다.**

두 단계로 반증됐다.

**1단계 — 스파인 끝이 경계에 닿으면 안 된다.** 조향은 블로커 하나의 실루엣, 즉 벽의
**끝 캡**을 겨눈다. 캡이 타원에 봉인되면 돌 곳이 없다.

| 레이아웃 | cinder-span | ash-march | cinder-sluice |
|---|---:|---:|---:|
| 벽까지 닿는 스파인 | 12.70 % | 22.92 % | 8.08 % |
| 끝을 300 px 띄움 | **0.00 %** | **0.00 %** | **0.00 %** |

**2단계 — 그래도 살아남지 못한다.** 분출구는 반경 90이고 복도 최소 150을 지키려면
스파인 선의 약 **470 px**를 무력화한다. 플레이필드는 1470 폭인데 양끝 개구부 300씩을
빼면 870이 남고, 분출구 둘이면 끝난다. 그런데 기믹은 **계약상 아레나 중심 부근에
고정**돼 있고(방벽주는 중심에서 아이소 220~280) 스파인이 지나려던 자리가 바로 거기다.
전수 실측: 손으로 배치한 스파인이 6스테이지 합쳐 **0~2조각** 생존.

**결론: 인테리어는 벽이 아니라 엄폐물로 짓는다.** 반경 40 엄폐물은 같은 분출구에서
280만 있으면 되고, 1470×780 타원에는 그 자리가 많다.

### 3.4 현재 구성 — 기믹의 순수 함수

`DungeonLayoutSpec.For(gimmicks, stageId)`는 스테이지별 손표가 아니라 **생성 함수**다.
결정론은 유지된다(RNG 없음, 순회 순서 의존 없음).

```
후보 격자   중심 오프셋 16점 (4행 × 4열, x를 비대칭으로 흩어 격자로 안 읽히게)
반경        46 / 40 / 44 / 38 순환      ← 동일 규격 반복(cover box) 금지
제외 1      중앙 성소 아이소 240 이내   ← 포컬 · 네거티브 스페이스 (§3.5)
제외 2      도달 타원 밖
제외 3      기믹에서 (r_g + r_c + 150) 이내
제외 4      조류 밴드 안              ← 밀려서 눌리면 낀다
제외 5      핀치: 다른 solid와 틈이 (0, 150)  ← 붙는 건 안전, 거의 붙는 게 함정
스파인      기믹이 성긴 2스테이지에만 (cinder-span · ash-march)
```

**제외 5가 이 파일의 핵심 규칙이다.** 전역 keep-out 반경으로는 표현할 수 없다 —
{20, 60, 100, 140}으로 스윕하니 ~50 % 스톨 스파이크가 **사라지지 않고 스테이지 사이를
옮겨 다녔다**(abyss-chancel@20 → ember-bastion@60 → echo-throne@100). 함정은 거리가
아니라 **쌍**이기 때문이다. 안전할 만큼 반경을 키우면 레이아웃이 전멸했다(6스테이지
합쳐 스파인 1조각). 좁은 틈을 만드는 그 조각만 버리면 나머지는 남는다.

48 px 복도뿐이라 놓을 자리가 구조적으로 없다. 그 스테이지의 인테리어는 조류 자체다.

### 3.4b 배치는 밀도보다 **위치**에 훨씬 민감하다

격자를 세 번 옮겨봤고 결과가 단조롭지 않았다.

| 격자 | 최악 스톨 |
|---|---:|
| 외곽 ±540 / 행 ±250, 스탠드오프 0.85 | 3.14 % |
| 외곽 ±480 / 행 ±200, 스탠드오프 0.78 | **90.71 %** (ash-march) |
| 외곽 ±440 / 행 ±250, 스탠드오프 0.85 | 2.89 % |

가운데 행은 엄폐물 **개수가 같고 위치만** 달랐다. 즉 이 지표는 "얼마나 놓았나"가
아니라 "어디에 놓았나"에 지배된다. 손튜닝으로 수렴시키려 하면 매번 주사위를 다시
굴리는 셈이므로, **격자를 바꿀 때는 반드시 프로브를 다시 돌린다.** 스톨 게이트는
그래서 이 파일에서 가장 값싸고 가장 중요한 안전장치다.

### 4.2 캡슐 블로커 — 추가형 (CLAUDE.md §4h 관례)

새 필드를 만들지 않는다. `HazardConfig`의 `HalfW`/`HalfH`(현재 TideCurrent 전용)를
**세그먼트 반벡터**로 재사용한다.

```csharp
public enum HazardKind { ..., AshWall = 5, StoneWall = 6 }   // 추가만, 재정렬 금지

public static HazardConfig Stone(float x, float y, float halfVecX, float halfVecY, float radius)
    => new HazardConfig {
        Kind = HazardKind.StoneWall,
        X = x, Y = y,                    // 세그먼트 중심
        HalfW = halfVecX, HalfH = halfVecY,  // 세그먼트 반벡터
        Radius = radius,                 // 캡슐 반경
    };
```

`ApplyPillars` → `ApplyBlockers`로 일반화. **아이소 공간에서 투영한다** (기존 원 처리가
`deltaY * IsoY`를 쓰므로 축이 갈리면 안 된다):

```csharp
// 아이소 좌표로: py' = (p.y - c.y) * IsoY, ay' = HalfH * IsoY
// t = clamp(((p'-c')·a') / (a'·a'), -1, 1)
// q' = c' + t·a'      →  이후는 기존 원 밀어내기와 동일 (target = Radius + actorRadius)
```

원(`ObsidianPillar`)은 `HalfW = HalfH = 0`인 캡슐의 특수해이므로 **한 루프가 둘 다 처리한다.**
중심 일치 시 +x 이젝트 규약(기존 `MoveEpsilon` 분기)은 그대로 승계.

### 4.3 조향 — 벽 슬라이딩 + 국소 접선

**슬라이딩**은 밀어내기의 자연 결과라 추가 코드가 없다 (매 틱 이동 후 표면 스냅 →
잔여 운동이 접선 성분만 남는다).

**접선 조향**은 적 전용이며 신규다:

```
매 틱, 각 적에 대해 (아이소 공간에서):
  d = player − enemy
  블로커 중 "enemy→player 선분을 (Radius + EnemyPushRadius) 안으로 가로막는 것" 수집
  없으면 → 기존 직선 추적 (변화 없음)
  있으면 → 가장 가까운 것 하나 선택
    두 접선 방향 계산 → d와의 각편차가 작은 쪽 선택
    동률이면 +x 쪽 (기존 데드센터 이젝트 규약과 동일한 결정론 타이브레이크)
    그 방향으로 이동, 가로막힘이 풀리면 즉시 직선 추적 복귀
```

- **비용**: `EnemyCap 20 × 블로커 15 = 300` 선분-원 테스트/틱. 고정스텝 60 Hz에서 무시 가능.
- **결정론**: 부동소수 연산만, 분기는 전부 비교. 정렬·해시 없음. 골든 재현성 유지.
- **한계**: 오목부 탈출 불가 → §3.6 규칙으로 방어.

### 5.3b 모델 이탈 기록 — meshy → tripo (2026-08-10 실측)

스펙이 지정한 `meshy_v6_text_to_3d`는 **이 CLI로 도달 불가**다.

```

       !params.enable_animation || params.enable_rigging
```

이건 규칙이 우리 파라미터를 **거절**한 게 아니라 CLI가 규칙을 **평가하지 못한** 것이다.
`generate cost`도 다른 규칙(`params.mode == "full" || ...`)에서 같은 방식으로 죽으므로
인자 조합으로 우회할 수 없다. (`gti`의 codex 프로바이더가 이미지 입력을 거부해 인트로 릴

`tripo_3d`로 전환: 제약 블록이 없고, 5 크레딧으로 견적이 통과하며, meshy에서 실제로
필요했던 유일한 파라미터인 폴리곤 상한을 `face_limit`으로 노출한다.

### 5.3d 정규화 계약과 그것을 두 번 놓친 방식

`kit_from_glb.py`는 모든 파트를 **한 자세**로 내보낸다:

```
최장 수평축 = +X   ·   X/Y 중심 = 원점   ·   최저 Z = 0   ·   최장 수평 길이 = 1.0
```

이 계약 덕분에 뷰의 스케일 인자가 곧 원하는 월드 크기가 되고, 런타임은 생성기가
무엇을 뱉었는지 몰라도 된다.

**같은 함정을 두 번 밟았다.** 회전이 적용되지 않는 것처럼 보였고, 먼저 오퍼레이터
컨텍스트(선택·활성)를 의심해 고쳤지만 그대로였다. 실제 원인은 `obj.bound_box`가
**캐시된 값**이라 depsgraph 갱신 전까지 이전 형상을 돌려준다는 것이었다 — 변환은
매번 적용되고 있었고 **계측만 낡아 있었다.** 정점에서 직접 재도록 바꾸자 즉시 맞았다.

프리뷰 카메라 사고(§5.3b)와 같은 계열이다: **정답과 오답이 같아 보이는 계측을 쓰면
그 위의 모든 추론이 무효다.** 두 번 다 원인을 코드에서 찾다가 계측에서 찾았다.

### 6.1 dotnet 심 프로브 (CLAUDE.md §4w — 유닛 없이 몇 초)

`CinderCourt.Sim`은 `UnityEngine` 참조가 없으므로 콘솔 앱으로 그대로 컴파일된다.

하네스: `scratchpad/simprobe`. `dotnet run` 1.8초 빌드 + 수초 실행.
**모든 기하 질문은 심의 `IsStandable`/`IsBlocked`를 호출해 묻는다** — 프로브가 타원과
캡슐을 다시 서술하면 그건 한 사실의 두 번째 출처가 되고, 이동 코드가 바뀐 뒤에도
계약값을 계속 보고한다 (§4i).

| 측정 | 게이트 | 최종 실측 |
|---|---|---|
| 이동 가능 면적 | ≥ 1.45 × 441,079 | 1.745~1.841× ✅ |
| 포켓 (우회율) | ≤ 2.5 | 1.16~1.73 ✅ |
| 연결성 | 단일 컴포넌트 | 6/6 ✅ |
| 적 스톨 | ≤ 4 % | 0.00~2.89 % ✅ |
| 결정론 | 동일 입력 2회 일치 | 6/6 ✅ |

**게이트 두 개는 실측 후 옮겼고, 옮긴 이유가 각각 다르다.**

- **이동 가능 면적 1.70 → 1.45**: 초안 예산이 액터 반경(민코프스키 합)을 빼먹어
  도달 불가능한 수였다. 계산이 틀렸던 경우다.
- **스톨 0 % → 4 %**: abyss-chancel은 중앙 기둥 때문에 **레이아웃이 0일 때 3.29 %**다.
  코드가 더 잘해서 통과할 수 없는 게이트는 그 작업을 재고 있지 않다. 그리고 같은
  스테이지가 레이아웃이 있으면 3.14 %로 **더 좋다** — 인테리어는 이 문제의 원인이
  아니라 완화 요인이다.

**스톨 지표의 귀속 절이 이 게이트의 전부다.** "정지 + 사거리 밖"만 세면 그건 링홀드를
재는 것이고, 초안 지표는 **블로커가 하나도 없는** ash-march에서 56.86 %를 보고했다.
지금은 "다음 걸음이 블로커 안으로 들어가는가"를 심에게 물어 귀속한다.

**조향의 변이 증명** (§4q). 최종 레이아웃에서 조향을 끄고 같은 측정:

### 6.3 브라우저 스모크 (CLAUDE.md §4c · §4l — 게이트 항목, 선택 아님)

```
bash tools/unity_batch.sh build → cd build-webgl && python3 -m http.server → 브라우저
```

[OBSERVED 2026-08-11] 빌드 통과: **에러 0, 84 MB**(예산 120 MB 내).
`build-webgl.data.unityweb` 71.2 MB · `wasm` 10.6 MB · `framework.js` 82 KB.

**[미완] 4모드 육안 확인을 끝내지 못했다.** 헤드리스 브라우저(Chromium)에서 Unity
로더는 뜨지만 진행 바가 움직이지 않는다. 150초까지 기다려도 같았다.

원인을 gzip 헤더로 의심해 검증했고 **반증됐다.** 빌드 산출물은 gzip이고
(`1f 8b 08`), `index.html`에 `decompressionFallback`이 없으며,
`python3 -m http.server`는 `Content-Encoding: gzip`을 보내지 않는다 — 그래서
헤더를 붙여 서빙하는 서버를 따로 세워 다시 시도했지만 **결과가 같았다.** 따라서
로더 정지의 원인은 압축이 아니라 헤드리스 환경에 WebGL 컨텍스트가 없는 것으로
보인다 [INFERENCE — 미측정].

**남은 [OBSERVED] 사실 하나는 따로 기록해 둔다.** 라이브 배포
(`akillness.github.io/hongT`)도 같은 gzip `.unityweb`를 `Content-Encoding` 없이
서빙한다(`content-length: 71201294`, 헤더 확인). 이게 실제 로딩을 막는지는
**확인하지 못했다** — 헤드리스가 어느 쪽이든 멈추므로 이 환경에서는 구분이 안 된다.
실제 브라우저에서 한 번 열어보면 즉시 판정된다. 이번 개정이 만든 문제는 아니다.

§4c의 요지는 "EditMode가 초록이어도 화면을 열면 더 나온다"이고, 이번 개정은 뷰를
크게 건드렸으므로 이 항목이 남아 있는 한 완료를 주장할 수 없다.

확인해야 할 것 — 이번 개정이 만든 것들:
- 벽 링이 프레임 안에 들어오는가 (계산상 e 1.097 vs 링 1.02, 여백 7.5 %)
- `StoneWall` 캡슐이 심의 충돌 형상과 같은 자리에 그려지는가 (§4k 계열 결함)
- Zone C 복원 후 맨바닥이 안 보이는가
- 외곽 밴드로 옮긴 드레싱이 4사분면에 고르게 보이는가
- 레인 통로가 읽히는가 — 넓어진 아레나에서 길을 잃지 않는가
- **4모드 전부**: Dungeon / Prologue / Training / Arena
