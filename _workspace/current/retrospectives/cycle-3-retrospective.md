## 2. 조사가 실제로 바꾼 것

이번 사이클의 설계는 세 문장으로 요약된다. **셋 다 조사 산출이지 취향이 아니다.**

1. **훈련의 빈 칸은 기믹이다** — 장르 11타이틀 전부 적·보스만 연습시킨다
   (T8 기믹 전용 시련 0/11). 이유는 구조적이다: RNG 게임에서 해저드는 재현이
   안 되므로 연습 대상이 못 된다. 우리 기믹 6종은 전부 고정 위상이다.
2. **돌발의 빈 칸은 조건이다** — 장르는 돌발을 시계로 만든다(3/13). 없는 것은
   시계 밖의 결정론 훅: 체력 임계(0/13), 누적 처치(0~1/13).
3. **보상 형태는 이미 정해져 있었다** — 장르 관례(반복 통화 지급 0/11)와 PM
   산술(유물 헤드룸 음수)이 독립적으로 같은 답을 냈다: 일회성/런스코프/비화폐.

특히 3번은 **두 레인이 서로 모르고 같은 결론에 도달한 사례**다. designer는
빈도표에서, PM은 드롭율 산술에서 출발했는데 같은 곳에 닿았다. 교차 검증의
가치가 이 사이클에서 가장 선명하게 드러난 지점.

## 3. 설계가 두 번 틀렸고 두 번 다 산술이 고쳤다

`design/training-and-surge-spec.md` §3.3은 이 사이클에서 **두 번 재작성**됐다.

| | 안 | 폐기 사유 | 잡은 것 |
|---|---|---|---|
| 초안 | 기믹 위상 이동 | 단조 가드(`cycle <= runtime.Cycle`)와 충돌 — 뒤로 밀면 영구 스킵 | 코드 읽기 |
| 2안 | 위기=시계 0.5배 (기본 효과) | 각인 없는 런에서도 발동 → **골든 15행 이동** | dotnet 프로브 |
| 확정 | 돌발은 심 상태, 효과는 각인 소유 | — | — |

확정안이 더 나은 설계인 이유가 중요하다. 서베이가 찾은 빈 칸은 "강화 3층 ×
돌발 5형태 = 0/15 채워짐"이었다. 돌발을 기본 효과로 만들면 **그 칸은 여전히
비고** 돌발은 또 하나의 자동 장치가 된다. 각인이 소유하게 하니 빈 칸이 정확히
채워졌다. **제약이 설계를 개선한 경우다.**

## 4b. 319/319 초록 뒤에 브라우저가 7건을 더 잡았다

이 사이클에서 가장 중요한 사실이다. **EditMode 319/319, 골든 무이동, 빌드
errors 0인 상태에서 게임을 열었더니 훈련장이 사실상 동작하지 않았다.**

| 결함 | 왜 테스트가 못 잡았나 |
|---|---|
| 훈련이 아레나 HUD로 렌더 — **기믹이 아예 안 그려짐** | `GameView`는 MonoBehaviour, EditMode가 안 돌린다 |
| 서지 배너가 화면에 없음(부모가 캔버스 밖) | 위와 동일 |
| 숙달 라벨이 버튼에 가림 | 레이아웃 테스트는 **버튼 크기**만 감사하고 라벨 겹침은 안 본다 |
| 제목 `— 웨이브 0/0`, 우상단 `웨이브 1 / 적 0` | 문자열 조합은 어느 어서션에도 없다 |
| 해류 두 대역이 같은 방향 | `CurrentPushSign`이 `CampaignStages`만 스캔 — 심은 옳고 **뷰만 틀렸다** |
| 해류 통로 20px | 배치 상수는 테스트가 값만 보고 **겹침을 안 본다** |
| 시련 종료/사망 문구가 던전 문구 | 문자열 계약 없음 |

**공통점**: 전부 **뷰 레인**이고, 전부 **사람이 화면을 봐야만** 보이는 것이다.
심 레인은 프로브·골든·23건 신규 테스트가 촘촘히 덮었지만, 그 심을 화면에
연결하는 배선은 어떤 자동 검증도 없었다.

### 특히 뼈아픈 것 — "심은 옳고 뷰만 틀렸다"

해류 시련은 `PushX`를 반대로 넣어 심에서는 **정확히 대향으로 밀고 있었다**.
화살표만 같은 방향으로 그려졌다. 즉 **기능은 맞는데 가르치질 못한다**.
시련의 존재 이유가 "순류와 역류의 감각을 익히는 것"인데 화면이 그걸 부정했다.
테스트로는 영원히 안 잡혔을 종류다.

### 방벽 시련은 설계 문서와 UI가 어긋나 있었다

스펙 표는 성공 판정을 "파괴한 방벽주 수"로 옳게 적었는데, 로비 UI는
"오라 안팎의 피해 차이"라고 안내했다. **오라는 적을 보호하는 장치**이고
시련은 적을 스폰하지 않으므로 그 레슨은 성립 자체가 불가능하다.
표와 화면이 다를 때 **플레이어에게는 화면이 계약**이다.

### 그리고 내 수정이 테스트를 깨뜨렸다

세리머니 제목을 빈 문자열로 바꿨더니 `PresentationFeedbackTests`가 실패했다 —
그 테스트는 패널을 **자식 텍스트 "구역 정화"로 식별**한다. 기본값을 되돌리고
시련일 때만 교체하도록 재수정. 래칫이 이번엔 나를 잡았다.

**교훈**: 뷰 레인에 "화면을 열어본다"는 게이트가 없으면, 심이 아무리 촘촘해도
플레이어가 만나는 것은 검증되지 않은 상태다. 다음 사이클부터 **뷰 변경이 있는
사이클은 브라우저 스모크를 게이트 항목으로 승격**한다.

## 5. 래칫이 설계를 바꾼 사례 (3번)

로비 터치 플로어 테스트는 "부채 표"다. 신규 위반은 결함, 이탈은 개선.
시련 카드마다 등급 버튼 3개(15개)를 넣었더니 28.3 CSS px — 기존 최악(41.0)보다
좁은 **새 위반 등급**이었다.

선택지는 둘이었다: 표를 넓히거나, 설계를 바꾸거나. 표를 넓히면 래칫이
무의미해진다. **설계를 바꿨다** — 등급 선택을 공유 카드 1장으로 올리고 시련
카드는 강하와 동일 문법의 버튼 1개만. 결과 신규 8개 전부 41.0, 새 위반 등급 0.

UX도 나아졌다: 등급을 한 번 고르고 5시련을 도는 것이, 시련마다 등급을 다시
고르는 것보다 실제 사용 흐름에 맞는다. **래칫이 UX를 개선했다.**

## 5b. 커버리지 — 결함 4번을 다시 못 만들게 고정

`Assets/Tests/EditMode/TrainingSurgeTests.cs` 23건 / 123 어서션.
전담 테스트 에이전트 작성, **프로덕션 무수정**으로 착지.

핵심은 회귀 1건이다:
`Surge_OpensExactlyOnceWhenOneTickJumpsOverAKillBoundary` — 하네스로 실제
멀티킬 점프 스크립트를 **찾아내서** 고정했다(cinder-span, nova 25틱 주기,
무스윙 → t2500에 kills 9→13). 양끝 9와 13이 **둘 다 12의 배수가 아니라서**
옛 `% 12 == 0` 구현이면 0회 열린다. 즉 이 테스트는 결함 4번을 정확히 재현한다.

검증 방식도 기록해둔다: 에이전트가 **뮤테이션 테스트 20건 중 16건 검출**을
자체 확인했다(심 사본을 패치하고 복원, 사후 바이트 동일 확인). 어서션이
실제로 무언가를 잡는지 스스로 증명한 셈이다.

또 하나 값진 것 — 순진한 테스트를 스스로 기각한 기록:
"수동 시련은 체력이 줄지 않으므로 `Trials_NeverOpenAWindow`의 초안은
공허(vacuous)했다" → 시련 자체 분출구 위에 파킹시켜 체력이 만피에서 0까지
35% 선을 관통하게 만든 뒤 그래도 0창임을 확인. **테스트가 통과하는 것과
테스트가 무언가를 지키는 것은 다르다**는 것을 실제로 구분했다.
