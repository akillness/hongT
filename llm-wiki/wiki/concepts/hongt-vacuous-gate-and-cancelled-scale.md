# 진공 게이트와 상쇄되는 스케일 — 기믹 지형 가구에서 배운 7가지

- 상태: [OBSERVED] (2026-08-07 세션, `Assets/Scripts/View/EnvironmentBuilder.cs` 기믹 가구 패스)
- 관련: [[wiki/concepts/hongt-environment-amendment-12]], [[wiki/concepts/hongt-companion-autonomy-tick-order-trap]]

각 항목은 이 세션에서 **실제로 초록을 통과한 채 살아남았던** 결함이다. 재발견 비용이 높아 남긴다.

## 1. 상한 단언은 0개일 때 진공 통과한다 [OBSERVED]

`EnvironmentBuilderTests`의 모든 기존 행은 상한("어떤 모듈도 …하면 안 된다")이거나 자식 순회다.
패스가 **아무것도 만들지 않으면 전부 통과**한다.

실제 사례: 조수(TideCurrent) 제방 레일이 `HalfW`를 써서 모듈 0개를 만들었는데
전체 스위트가 초록이었다. 이름만 맞고 렌더러 없는 빈 피벗도 같은 형태로 통과한다.

- 교훈: 새 생성 패스에는 **양성 단언**을 함께 넣는다 —
  "이 조건의 스테이지는 최소 1개를 만든다", 그리고 **렌더러를 요구**한다.
- 이름 카운트만으로는 부족하다. `Materialize`는 조각 루프 전에 피벗을 만들고,
  라이브러리 로드 실패 시 조용히 반환하므로 빈 피벗이 남는다.

## 2. 곱한 뒤 캡을 씌우면 인자가 대수적으로 소거된다 [OBSERVED]

```
scale = localScale · SizeY           // 의도: 파츠별 크기 문법
h₀    = height(scale)                 // = h_src · SizeY
if h₀ > cap: scale ·= cap / h₀        // = localScale · cap / h_src
```

`SizeY`가 **사라진다**. 파츠별 9/10/11/12 문법이 전부 같은 캡 높이로 납작해진다.
캡이 거의 항상 걸리므로 문법 전체가 무력화된다.

- 교훈: 크기 필드는 **배율이 아니라 목표값(target)** 으로 정의하고 직접 풀어라.

## 3. 축 이름을 확인하라 — HalfW ≠ 세로 반높이 [OBSERVED]

`CampaignSpec.CurrentHalfW = 520`(X 반폭, 아레나 반폭과 동일),
`CurrentHalfH = 110`(Y 반높이). 밴드의 세로 두께는 `HalfH`다.

`HalfW`로 오프셋을 잡으면 좌표가 아레나(y 334~874) 밖으로 나가 전부 컬링된다.
그리고 §1 때문에 **게이트는 초록**이다.

- 부수 결론: 조수 밴드는 y 360-580 / 630-850을 덮어 여유가 26/50/24px뿐이고,
  가운데 50px는 스펙이 명시한 유일한 안전 회랑이라 장식을 두면 안 된다.
  AshWall과 함께 "국소 실루엣이 없는 밴드 기믹"으로 분류해 제외했다.

## 4. 높이만 구속하면 XZ가 부풀어 텔레그래프를 덮는다 [OBSERVED]

높이 목표로 스케일을 풀면 XZ도 같은 배율로 커진다. 납작한 데칼일수록 `h₀`가 작아
배율이 커지고, 실측 XZ 반폭이 **0.701u(70 sim px)** 까지 갔다.

링 마진 12px 기준 벤트 가구 피벗은 152px인데 안쪽 모서리는 81.9px —
**반경 90 피해 디스크 안**이었다. 클리어런스 테스트는 **피벗만** 보므로 초록.

- 교훈: 높이와 발자국 **둘 다** 구속하고 `min`을 취한다.
- 마진이 곧 실루엣 예산이다: 피벗을 `Radius+ClearBase+margin`에 두고
  반폭을 `margin` 이하로 캡하면 안쪽 모서리가 클리어런스 선에 정확히 걸린다.
- 폐색은 산수로 확인 가능: `0.34/tan(55°) = 23.8px < ClearBase 50`.

## 5. 색조는 해저드 채널을 침범할 수 있다 [OBSERVED]

가구가 바닥과 구분되지 않아 강조색(ember)으로 올리려 했으나,
벤트 텔레그래프가 `Color(1, 0.6, 0.3)` — **주황이 이 스테이지의 해저드 채널**이다.
장식에 같은 색조를 주면 위장이 되어 §E0.5를 더 크게 깬다(안 보이는 것보다 나쁘다).

- 대신 **명도**로 분리: `tints.Stone`(0.155) 기반에 charred 배율,
  바닥 패널(`floorBase` 0.235)보다 어둡게.
- 그림자는 쓸 수 없다 — env 라이트는 전부 `LightShadows.None`이고
  가구도 `shadowCastingMode.Off`다. 명도가 유일한 채널이다.
- 결과 [OBSERVED, 2026-08-07 배포 04a29b9]: 틴트는 **먹었다** —
  가구 0.115~0.270 vs 바닥 0.371, 최암부 **3.23×** 분리(게이트 실측).
  좌표도 독립 확인: `env-floor-500` sim(480,636) = 벤트(560,480)에서 175px,
  링 반경 170 + 지터 범위와 일치.
- 그러나 화면에서는 **바위가 아니라 그을음 자국**으로 읽힌다.
  의도했던 "authored 바위 실루엣"에는 미달이다. 목표 미달을 기록해 둔다.
- ~~여기서 Shade를 더 낮추면 안 된다. 원인은 Zone A **붉은 안개**이고 남은
  레버는 `CameraRig` 안개 밴드다.~~ **[RETRACTED 2026-08-07]** 이 결론은
  오염된 측정에서 나왔다 — 아래 §6 참조. 배포본 안개는 붉지 않다.
- 측정 범위 주의: 게이트가 읽는 값은 MPB 틴트라 **안개·조명 이전**이다.
  "틴트가 안 먹었나 / 먹었는데 프레임이 먹었나"는 가르지만,
  화면 가독성 자체를 증명하지는 못한다.

## 6. HUD 오버레이가 씬 색 측정을 오염시킨다 [OBSERVED]

§5의 "붉은 안개" 결론은 **틀렸다**. 스크린샷으로 씬 색을 판정할 때
HUD 상태를 고정하지 않은 것이 원인이다.

- 붉게 보인 정체: `HudView.cs:2862`의 피격 비네트 `Color(0.95,0.22,0.13)`,
  알파 0.6, `SimEvents.PlayerDamaged`에서 발화. 방사형 그라디언트
  (`MakeRadialTexture`: r<0.45는 알파 0, 이후 SmoothStep).
  저체력(`Health < 35`) 비네트도 같은 색이나 `SimMode.GameOver`에서는 꺼진다.
- 실측 대비 [OBSERVED]:
  피격 프레임 가장자리 `(175,47,33)` vs 무피격 `(60,37,35)`.
  붉은 우세 픽셀 80.9% → 47.9%.
- **[RESOLVED 2026-08-08]** 질문 자체가 틀렸다. "런타임이 배경색을 덮어쓴다"는
  전제였는데, `Assets/Scripts/View` 전체에 `backgroundColor`/`clearFlags`
  **쓰기가 0건**이다(StageMood는 `ambientLight`/`fogColor`만, CameraRig는
  안개 거리만 건드린다). 즉 그 픽셀은 **카메라 배경이 아니다**.
  55° pitch / FOV 42면 프레임 상단 레이도 수평 아래를 향해 하늘이 없으므로
  clear color는 화면에 0%다.
  실측 `~(60,37,35)`의 정체는 **`fogColor` 쪽으로 블렌드된 조명 받은 지면** —
  이미 별도로 증명한 "`fogEnd` 밖 지면이 단색으로 치환된다"와 같은 표면이다.
  그 단색은 **StageMood의 스테이지별 accent 안개**다. 색조 서명이 가른다
  (R로 정규화한 R:G:B):
  - SceneBuilder authored fog `1 : 0.91 : 1.12` — 차가움, B 우세
  - StageMood `FogColor(accent)` `1 : 0.72 : 0.70` — 따뜻함, R 우세
  - 측정치 `1 : 0.62 : 0.58` — 따뜻함
  `cinder-span` accent는 `(0.95,0.35,0.17)`(StageCatalog L165)이고
  `FogColor = accent*0.12 + (0.020,0.024,0.036)`이다.
  절대값은 계산치(102,73,71)보다 어두운데, 표본에 지오메트리가 섞이고
  포스트 볼륨(bloom/vignette)을 거치기 때문으로 본다 [INFERENCE].
  색조 방향은 명확하므로 "SceneBuilder 드리프트" 가설은 기각한다.
- 그래도 "프레임이 평탄하게 비어 있다"는 판정은 **살아남는다**:
  비네트는 그라디언트라 버킷을 **쪼갠다**. 오염 상태에서 단일 버킷이
  74.3%였다면 그건 상한이 아니라 **하한**이고, 무피격 실제 평탄도는 더 높다.
- 교훈: 스크린샷으로 색을 판정하기 전에 HP·피격 타이머 같은 **HUD 상태를
  먼저 고정**하라. 색 확인만 필요하면 비네트 알파가 0인 **중심 반경 45% 안**을
  샘플링하면 HP와 무관하게 깨끗하다(단 중심은 아레나라 여백 비율에는 편향).

## 7. 파생 상수는 따라가고, raw 상수는 조용히 표류한다 [OBSERVED]

같은 세션에서 두 상수가 정반대로 갈렸다. 비싼 쪽은 후자다.

**따라간 쪽**: `FurnitureMaxHalfExtent`를
`FurnitureRingMargin * ViewWorld.Scale` const 식으로 두었더니,
다른 레인이 `ViewWorld.Scale`을 0.01 → 0.0125로 바꿨을 때
예산이 0.30 → 0.375로 **스스로 따라갔다**. 마진 30 sim px는 불변이므로
기하 불변식(안쪽 모서리 = `Radius+ClearBase`)도 유지됐다.

**표류한 쪽**: `FurnitureMaxHeight`는 raw `0.34f`(구 배율에서 34 sim px)였다.
Scale이 바뀌자 아무 경고 없이 **27.2 sim px로 20% 조여졌다**.
게이트는 계속 초록이었고, 하마터면 움직인 캡을 기준으로 Shade를 튜닝할 뻔했다.

- 교훈: "파생 상수는 좋다"가 아니라 **"raw로 남긴 하나가 표류한다"** 가 요점이다.
  월드 단위 리터럴은 전부 표류 후보다.
- 리포 관례는 두 가지다:
  `ViewWorld.LegacyScaleRatio`로 보정(`CameraRig.cs` L20/L22,
  `EnvironmentBuilder.cs` L148-149 라이트 반경), 또는
  애초에 **sim px로 표현**해 `Scale`을 곱하는 것.
  기하 제약(ClearBase, Radius)이 sim px 단위이므로 후자를 택했다:
  `FurnitureMaxHeightPx = 34.0` → `* ViewWorld.Scale`.

## 8. 곱셈은 두 번 걸린다 — MPB 틴트 × authored albedo [OBSERVED]

이 세션에서 **세 번** 같은 실수를 했다. 매번 "적용했는데 화면이 안 변한다"로 나타났다.

1. VoidFloor: `_BaseColor(0.105) × stone albedo(0.336) = 0.035`.
   파일 자신이 "0.055는 이미 실패"라고 적어둔 값보다 어두웠다.
2. 실루엣: `tints.Stone(0.155) × Shade(0.88) × FBX albedo(~0.35) = 0.048`.
   내부 휘도 1.22, 바닥의 34배 어두움, std 0.58 = 완전 평면 컷아웃.
3. 두 경우 다 커밋 메시지에 "밝기는 유지된다"고 **확인 없이** 적었다.

- 규칙: URP Lit/Unlit 모두 `_BaseColor × _BaseMap`이다. authored 머티리얼에
  이미 텍스처가 물려 있으면 MPB 틴트는 **두 번째 곱**이다.
- 보정: 목표 휘도 ÷ albedo 평균. 값을 고르지 말고 **역산**하라.
- 검증: 배포 프레임에서 대상 영역과 기준 영역(바닥 등)을 함께 샘플링해
  비율로 판정. MPB 값만 읽으면 안개·조명 이전이라 화면 결과를 증명하지 못한다.

## 9. 라이트 예산 상한 4는 POINT 라이트 전용 [OBSERVED]

"링이 라이트 사거리 밖이라 앰비언트만 받는다"고 커밋에 적었으나 **틀렸다**.

- `StageMood.Apply`의 key(0.55)/fill(0.22)는 `LightType.Directional`이다
  (`DungeonFramingAndMoodTests`가 그걸 단언한다). 방향광은 거리 감쇠가 없어
  아레나 밖 어디든 동일하게 도달한다.
- §E6의 상한 4는 포인트 라이트 예산이고 방향광은 무관하다.
- 따라서 실루엣 std가 낮은 원인은 조명 부재가 아니다. **미확정**이며 후보는
  ① key/fill 강도가 얕아 명암 대비 부족, ② authored feature albedo가 평탄,
  ③ 프레임 점유 픽셀이 적어 표본이 작음.

## 10. emissive는 주변을 비추지 않는다 [INFERENCE]

키아트의 "다수 따뜻한 광원"을 emissive 머티리얼로 재현할 때 주의:
실시간 GI가 없는 URP Forward + WebGL에서 emissive는 **자기 픽셀만** 밝다.
따라서 실루엣 옆에 emissive 횃불을 세워도 실루엣 표면 명암(std)은 안 변한다.
목표를 "std 개선"이 아니라 **"프레임에 광원 점 추가"** 로 적어야 결과를 오판하지 않는다.

## 11. 지표와 목표가 갈리는 지점이 있다 [OBSERVED]

지배 색 버킷은 환경 개선의 계기판으로 썼고 85.8% → 53.7%까지는 잘 맞았다.
그런데 실루엣을 밝히자 **지표는 나빠지고(49.7 → 54.2) 그림은 좋아졌다**.
검은 실루엣이 그 자체로 별도 버킷을 만들어 지표를 낮추고 있었기 때문이다.

- 교훈: 대리 지표는 어느 구간까지만 유효하다. 지표가 목표와 갈리기 시작하면
  지표를 좇지 말고 **그 지점을 기록하고 다른 계기판으로 갈아타라**.
- 이 구간의 대체 기준: 대상/기준 영역의 (평균 비율, std 비율, 채도 격차) 3종.

## 12. 픽셀 지표는 프로토콜에 종속된다 [OBSERVED 2026-08-08]

지배 색 버킷을 9스테이지 랭킹에 쓰려다 실패했다. 실측:

| | echo-throne 지배% |
|---|---|
| 동일 프로토콜 3회 | 54.5 / 54.6 / 54.6 — 스프레드 **0.1pt** |
| 다른 프로토콜(진입 직후 캡처) | 20.8 — **33.8pt** 차이 |

- 프로토콜 안에서는 거의 완벽히 재현된다. 스프레드는 전부 **캡처 시점**에서 온다.
- 원인은 "적이 많아서"가 **아니다**. 그러면 늦게 잡을수록 다양해져 지배%가
  내려가야 하는데 실측은 반대였다. 실제 기전은 **두 종류의 전면 오버레이**이고
  서로 반대 방향으로 민다:

  | 오버레이 | 성질 | 지배%에 미치는 영향 | 실측 |
  |---|---|---|---|
  | 해저드 텔레그래프(조류 밴드·벤트 디스크) | **평탄** 단색 | **올림** | R+3.2s → 54.5 |
  | 피격 비네트 | **그라디언트**(방사형) | **내림** | R+6.0s → 22.0 |

  판별식: 프레임 네 모서리의 R/G. 1.6 초과면 비네트 활성.
  실측 3.2s는 1.06(깨끗), 6.0s는 3.32(비네트).
- 전투 중 프레임은 둘 중 하나 또는 둘 다를 항상 갖는다. **벽시계 오프셋으로는
  못 피한다** — 늦추면 비네트, 당기면 텔레그래프다.
- 따라서 **같은 프로토콜의 A/B**에는 유효하고(이 세션의 환경 진행 85.8→39.0은 그 조건을 만족),
  **스테이지 간 랭킹**에는 프로토콜을 고정해도 여전히 게임플레이 내용물이 섞인다.

### 스윕을 오염시킨 3종 [OBSERVED]

1. **딥링크 무음 실패** — 잠금 해제 형식을 틀리면(`cleared` 배열 vs 실제 `clearedMask` 정수)
   `GameDirector`가 `EnterLobby()`로 조용히 떨어진다. 에러가 없어 **로비 3장이 던전으로 집계**됐다.
   단서는 "수치가 4자리까지 동일".
2. **localStorage 리셋** — 이전 evaluate에서 세운 값이 내비게이션에 날아간다.
   저장과 이동을 같은 스텝에서 해야 한다.
3. **패배 스크림** — Lv1 딥링크는 즉사한다. 사망 오버레이는 중앙 패널만이 아니라
   **씬 전체를 어둡게 덮어** 평탄화한다(ember-bastion 59.1 → 재캡처 26.5).
   중앙 마스크로는 못 뺀다. 중앙 1/3의 근균일 블록을 검출해 프레임을 버려야 한다.

### EditMode 렌더로 옮기려다 만 이유 [OBSERVED]

`Camera.Render` → `RenderTexture` → 히스토그램이면 HUD·VFX·액터 없는 결정론
프레임을 얻는다. 그런데 `tools/unity_batch.sh`는 `tests`와 `method` **둘 다**
`-nographics`로 돌린다(L46/L53). 그 상태에서 렌더는 빈 텍스처를 내므로 게이트가
**빈 텍스처를 측정하며 초록**이 된다 — 이 문서 §1의 진공 게이트 그대로다.
가려면 그래픽 활성 호출을 따로 두고 **결과 픽셀 분산이 0이 아님을 먼저 단언**해야
한다. 아니면 렌더 없이 `EnvironmentLayout.Compute` + 스테이지 텍스처
`GetPixels32` 히스토그램으로 해석적으로 비교한다(헤드리스 안전).

### 유효한 사용법

- 같은 프로토콜(진입 방식·경과 시간·HP 상태 고정)으로 전후를 비교할 것.
- 프레임마다 (지배%, 버킷 수, 평균 휘도, std, 채도) 5종을 함께 남길 것 — §11대로
  지배 버킷 단독은 어느 구간부터 목표와 갈린다.

## 13. 실루엣 std 0.31은 창(window) 산물이었다 [RESOLVED 2026-08-08]

§9가 미확정으로 남긴 "실루엣 std 비율 0.31(목표 0.50)"을 닫는다. 결론:
**지표가 잘못 읽혔고, 원인 후보 3개는 전부 기각된다.**

측정 1 - 0.31은 재현되지 않는다. 배포본 한 프레임에서 표본 창만 바꿔 7회:

| 창 | std 비율 |
|---|---|
| 좌측 가장자리 dark<90 | 0.500 |
| 좌측 가장자리 dark<60 | 0.460 |
| 우측 가장자리 dark<90 | 0.563 |
| 전체 프레임 dark<60 / <90 / <120 | 0.478 / 0.561 / 0.669 |
| 플레이트 바깥 좌측 | 0.527 |

동일 프레임에서 **0.46~0.67, 스프레드 45%**. 목표 0.50은 이 폭 안에 있다.
§12가 "지배 버킷은 프로토콜에 종속된다"고 적었는데, std 비율은 한 걸음 더
나쁘다 - **같은 프로토콜, 같은 프레임에서도 창만 바꾸면 갈린다**.

측정 2 - 후보 ② authored albedo 평탄은 **반증**. 기둥 하나를 세로열로 잘라
가로 프로파일을 재면 30.05 -> 20.18 -> 42.67 (범위 22.5), 열 내부 std 평균은
7.33. 신호가 노이즈의 3배다. 방향광 아래 원통이 음영지는 바로 그 모양이므로
표면은 셰이딩되고 있다. ①(key/fill 얕음)도 따라서 불필요, ③(표본 작음)은
n=26k~247k에서 무의미.

측정 3 - 이 구간에서 std 비율 자체가 계기판으로 부적합. 알려진-불량(평평한
검은 컷아웃, 코드에 기록된 mean 1.22 / std 0.58)과 현재 양품을 비교하면:

| 지표 | 불량 | 양품 | 분리도 |
|---|---|---|---|
| 변동계수 std/자기평균 | 0.475 | 0.409 | **1.16x** (판별 불가) |
| mean 비율 statue/floor | 0.029 | 0.519 | **17.6x** |
| std 비율 (바닥 std 대비) | 0.014~0.058 | 0.500 | ~10x |

변동계수는 못 가른다. std 비율은 가르지만 창 민감도 45%를 안고 간다.
mean 비율이 가장 강하고, 무엇보다 **소스 자신의 합격 기준**(EnvironmentBuilder
.cs:1024-1027 "바닥보다 어둡되 구멍은 아닌 어두운 덩어리")이 곧 mean 비율이다.
현재 0.52로 충족.

- 교훈: 지표를 고치기 전에 **그 지표가 알려진-불량과 알려진-양품을 가르는지**
  먼저 확인하라. §11은 "지표가 목표와 갈리면 갈아타라"였고, 여기서는 한 단계
  앞이다 - 애초에 가르지 못하는 지표를 목표로 올려놨었다.
- 조치: std 비율을 폐기하고 mean 비율을 유지 지표로 쓴다. 높은 내부 std는
  오히려 "정교하게 모델링된 자기음영 조각상"을 뜻해 키아트 방향(어두운 덩어리)과
  싸운다.

## 14. 캡처 프레임 ≠ 렌더 뷰포트 [OBSERVED 2026-08-08]

"§E1.5 Zone C를 프러스텀 끝까지 확장" 작업을 열어놓고 코너 점유율을 쟀더니
82~84%(중앙 99.9%)가 나왔다. 16~18%가 비었으니 모듈을 더 세워야 하는 것처럼
보였다. **전부 페이지 레터박스였다.**

- 캡처는 1600×1000인데 캔버스 백킹은 **1501×1000**. 차이 99px가 좌우
  50px씩 남고, 그 픽셀은 씬이 아니라 `body` 배경 `#050812`다.
- 판별이 쉬웠던 이유: 그 띠가 **완전 균일 단색**이고, 스테이지 안개색
  (60,37,35 계열)과 아예 다른 색이었다. 씬 픽셀이면 안개/포그가 섞여
  균일할 수 없다.
- 레터박스를 제외하고 다시 재면 코너 **98.1~99.9%**. 확장할 공백이 없다.
- EditMode 커버리지 게이트는 이미 bare=0.0000(한계 0.02)으로 같은 결론을
  해석적으로 내고 있었다. 픽셀 측정이 게이트와 어긋났을 때 **게이트가 맞았다**.

- 교훈: 화면 픽셀로 기하를 판정하기 전에 **캔버스 실제 범위부터 확정하라**
  (`getBoundingClientRect` + `canvas.width/height` + `devicePixelRatio`).
  캡처 해상도를 뷰포트로 착각하면 존재하지 않는 결함을 만들어낸다.
- §12·§13이 "픽셀 지표는 프로토콜/창에 종속된다"였다면, 여기는 한 층 더
  아래다 - **좌표계 자체가 틀렸다**.
